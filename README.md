# 📖 Executive Summary

Modern software delivery is no longer limited to building and deploying applications. Organizations must continuously secure, monitor, validate, and govern every stage of the Software Development Life Cycle (SDLC).

**SentinelOps** is an **Enterprise DevSecOps Security Orchestrator Framework** that integrates cloud infrastructure provisioning, secure CI/CD pipelines, container security, Kubernetes orchestration, compliance validation, monitoring, and runtime security into a unified platform.

Unlike traditional CI/CD projects that stop after deployment, SentinelOps focuses on the **complete security lifecycle**. Security findings generated by multiple scanners are collected, normalized into a common schema, enriched with compliance mappings, and presented through centralized dashboards for continuous visibility.

SentinelOps demonstrates how an enterprise can automate infrastructure provisioning, build secure software delivery pipelines, deploy applications on Kubernetes, monitor production environments, and continuously evaluate security posture using industry-standard DevSecOps practices.

### Security Challenges

Security tools operate independently.

Examples:

- Bandit
- Gitleaks
- Trivy
- Semgrep
- OWASP ZAP

Each tool generates reports in different formats.

Developers must manually:

- Open reports

Traditional deployment pipelines often lack:

- Security validation
- Vulnerability management
- Automated rollback
- Infrastructure monitoring
- Compliance reporting

Organizations frequently use disconnected monitoring tools, making it difficult to answer questions such as:

- Is the application healthy?
- Which deployment introduced a vulnerability?
- Are Kubernetes resources healthy?
- Is the infrastructure compliant?

# Infrastructure Components

## Amazon VPC

The Virtual Private Cloud (VPC) provides complete network isolation for the SentinelOps platform.

Responsibilities:

- Private networking
- Traffic isolation
- Secure communication
- Resource segmentation

---

## Public Subnets

The public subnet hosts resources that must be accessible from the Internet.

Resources deployed:

- Jenkins Server
- Application Load Balancer
- NAT Gateway

Why?

External users and GitHub webhooks must communicate with Jenkins and the Load Balancer.

---

## Private Subnets

All production workloads execute inside private subnets.

Resources include:

- Amazon EKS
- Backend Pods
- Frontend Pods
- Prometheus
- Grafana
- Alertmanager

This prevents direct Internet access to application workloads.

---

## Jenkins EC2

Jenkins acts as the Continuous Integration server.

Responsibilities:

- Source Code Checkout
- Security Validation
- Docker Image Build
- Push Images to Amazon ECR
- Deploy Helm Releases
- Trigger Kubernetes Rollouts

Jenkins is intentionally deployed outside the Kubernetes cluster to separate CI infrastructure from application workloads.

---

## Amazon Elastic Container Registry (ECR)

Amazon ECR stores all Docker images generated during the CI pipeline.

Images stored:

- Frontend
- Backend

Every deployment pulls container images directly from ECR.

Benefits:

- Secure image storage
- Version control
- High availability
- IAM integration

---

## Amazon Elastic Kubernetes Service (EKS)

Amazon EKS is the core runtime platform of SentinelOps.

Responsibilities:

- Container orchestration
- Service scheduling
- Self-healing
- Horizontal scalability
- Rolling updates
- Rollbacks

Every application component runs as Kubernetes workloads.

---

## Amazon Elastic Block Store (EBS)

Persistent storage is required for monitoring components.

Amazon EBS provides persistent volumes for:

- Grafana
- Prometheus
- Alertmanager

Without persistent volumes, monitoring data would be lost whenever Pods restart.

## IAM

Identity and Access Management (IAM) controls access to AWS resources.

SentinelOps uses IAM roles to allow:

- Jenkins → Amazon ECR
- Jenkins → Amazon EKS
- EKS Worker Nodes → ECR
- EBS CSI Driver → Amazon EBS
- AWS Load Balancer Controller → ALB

This follows the Principle of Least Privilege.

# Why Kubernetes?

Traditional deployments rely on manually running applications on virtual machines.

This approach introduces several challenges:

- Downtime during deployments
- Manual scaling
- Difficult rollbacks
- Lack of self-healing
- Operational overhead

Kubernetes addresses these limitations by providing:

- Automated Scheduling
- Rolling Updates
- Automatic Rollbacks
- Self-healing
- Horizontal Scaling
- Service Discovery
- Load Balancing
- High Availability

For SentinelOps, Kubernetes serves as the orchestration layer that manages application deployment, monitoring components, and future security services such as Wazuh and Argo CD.

---

# Why Helm?

Managing raw Kubernetes YAML files becomes increasingly difficult as applications grow.

Helm simplifies Kubernetes deployments by introducing reusable templates and configurable values.

Benefits:

- Reusable Kubernetes templates
- Environment-specific configuration
- Version-controlled deployments
- Easy upgrades
- Easy rollbacks

Instead of maintaining dozens of YAML manifests manually, SentinelOps packages the entire application into a Helm Chart that can be deployed with a single command.

# Phase 1 – Secure Development

Development begins on a feature branch.

Before code is committed, local validation helps identify common issues as early as possible.

Current validation includes:

- Secret detection
- Static code analysis
- Code quality checks
- Dependency auditing

This "shift-left" approach reduces the likelihood of insecure code entering the central repository.

---

# Phase 2 – Source Control

After local validation succeeds:

- Changes are committed
- Code is pushed to GitHub
- Pull requests can be reviewed and merged
- GitHub Webhooks notify Jenkins automatically

Git becomes the single source of truth for both application code and infrastructure definitions.

---

# Phase 3 – Continuous Integration

GitHub triggers the Jenkins pipeline.

The pipeline performs:

- Repository checkout
- Build preparation
- Security validation
- Container image creation
- Deployment automation

Every build follows the same reproducible process.

---

# Phase 4 – Security Validation

Security validation is integrated directly into the CI pipeline.

Current security stages include:

## Gitleaks

Purpose:

Detect accidentally committed secrets such as:

- AWS Keys
- API Tokens
- Passwords
- Private Keys

---

## Bandit

Purpose:

Static security analysis for Python components and scripts.

Detects:

- Insecure functions
- Dangerous subprocess usage
- Weak cryptography
- Hardcoded credentials

---

## Semgrep

Purpose:

Language-aware static analysis.

Detects:

- SQL Injection
- Command Injection
- XSS
- Insecure APIs
- Misconfigurations

---

## Trivy

Purpose:

Container image vulnerability scanning.

Detects:

- Critical vulnerabilities
- High vulnerabilities
- Medium vulnerabilities
- Low vulnerabilities

Scans both operating system packages and application dependencies.

---

## OWASP ZAP

Purpose:

Dynamic Application Security Testing (DAST).

Detects:

- Cross-Site Scripting
- SQL Injection
- Missing Security Headers
- Session Management Issues
- Authentication Weaknesses

# Compliance Mapping Engine

Organizations often need to understand not only *what* the vulnerability is, but also *which compliance requirements it affects*.

The SentinelOps architecture includes a Compliance Engine that associates security findings with recognized frameworks.

Target frameworks include:

- NIST Cybersecurity Framework (CSF)
- ISO/IEC 27001
- OWASP Top 10
- CIS Controls

Example workflow:

```text

      │

      │
```

This enables a security team to view technical findings alongside governance and compliance requirements.
