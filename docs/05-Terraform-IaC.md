# 1. Introduction

Provisioning enterprise cloud infrastructure manually is time-consuming, error-prone, and difficult to reproduce consistently across environments.

SentinelOps adopts **Infrastructure as Code (IaC)** using **Terraform** to automate the provisioning of AWS resources. Every infrastructure component required by the platform is defined declaratively in Terraform configuration files, allowing infrastructure to be version-controlled, reviewed, and deployed consistently.

Infrastructure changes follow the same Git-based workflow as application code, enabling repeatable deployments and reducing configuration drift.

---

# 2. Why Terraform?

Terraform was selected because it provides a cloud-agnostic, declarative approach to infrastructure provisioning while integrating seamlessly with AWS.

Key benefits include:

- Infrastructure as Code
- Version-controlled infrastructure
- Repeatable deployments
- Modular architecture
- Automated provisioning
- Simplified disaster recovery
- Environment consistency
- Dependency management

Instead of creating resources manually through the AWS Console, Terraform provisions the complete cloud environment using reusable modules.

---

# 3. Infrastructure as Code

Infrastructure is treated exactly like application code.

Every resource—including networking, compute, container registry, and Kubernetes—is described in configuration files and stored in Git.

This enables:

- Code review for infrastructure changes
- Version history
- Rollback through Git
- Automated provisioning
- Standardized environments

# 5. Terraform Workflow

Infrastructure provisioning follows a standard Terraform lifecycle.

```text
Developer

↓

Terraform Init

↓

Terraform Validate

↓

Terraform Plan

↓

Terraform Apply

↓

AWS Infrastructure Created

↓

Configure kubectl

↓

Deploy Applications
```

Each command serves a distinct purpose:

### terraform init

- Downloads required providers
- Initializes backend (if configured)
- Prepares the working directory

### terraform validate

- Validates configuration syntax
- Checks resource references
- Detects configuration errors before deployment

### terraform plan

- Generates an execution plan
- Shows proposed infrastructure changes
- Allows review before applying changes

### terraform apply

- Creates or updates AWS resources
- Resolves dependencies automatically
- Produces outputs for downstream use

# 6. Terraform Modules

SentinelOps uses a modular Terraform design.

## Network Module

Responsibilities:

- Create VPC
- Create public subnets
- Create private subnets
- Configure Internet Gateway
- Configure NAT Gateway
- Create Route Tables
- Configure Security Groups

---

## IAM Module

Responsibilities:

- Create IAM Roles
- Attach IAM Policies
- Configure AWS permissions
- Support secure access between AWS services

---

## EC2 Module

Responsibilities:

- Provision Jenkins EC2 instance
- Configure networking
- Associate Security Groups
- Configure SSH access

The Jenkins server hosts the CI/CD pipeline responsible for building, scanning, and deploying the application.

---

## ECR Module

Responsibilities:

- Create Backend Repository
- Create Frontend Repository

Amazon ECR stores versioned container images generated by the CI pipeline.

---

## EKS Module

Responsibilities:

- Create Amazon EKS Cluster
- Create Managed Node Groups
- Configure cluster networking
- Provision worker nodes
- Enable Kubernetes orchestration

Additional integrations such as IAM Roles for Service Accounts (IRSA) support components like the EBS CSI Driver.

---

## RDS Module

The repository includes an RDS module to support future managed database deployments. Depending on the current implementation, this module may be reserved for future use.

# 8. Terraform State Management

Terraform tracks infrastructure using a state file.

The state records:

- Existing resources
- Resource identifiers
- Current infrastructure configuration
- Dependencies

Terraform compares the desired configuration with the current state to determine which resources need to be created, updated, or destroyed.

> **Note:** The current project uses a local state file. For production environments, a remote backend (such as Amazon S3 with DynamoDB state locking) is recommended to improve collaboration and state consistency.

```text

↓

↓
```

```text

↓

Validate Configuration

↓

Review Execution Plan

↓

Apply Changes

↓

AWS Resources Updated
```

This process minimizes configuration errors and provides visibility into infrastructure modifications before they are applied.

# 11. Best Practices

SentinelOps follows several Infrastructure as Code best practices:

- Modular Terraform configuration
- Reusable infrastructure components
- Version-controlled infrastructure
- Principle of Least Privilege for IAM
- Automated provisioning
- Declarative resource definitions
- Environment-specific variables
- Infrastructure validation before deployment

Future enhancements include:

- Remote state backend (Amazon S3)
- State locking (DynamoDB)
- Multi-environment workspaces
- Policy-as-Code validation
- Automated cost estimation
- Infrastructure compliance scanning

# 12. Summary

Terraform forms the foundation of SentinelOps by automating the provisioning of AWS infrastructure.

Through reusable modules, declarative configuration, and Infrastructure as Code principles, Terraform enables SentinelOps to deploy a secure, scalable, and reproducible cloud environment that supports Kubernetes orchestration, CI/CD automation, monitoring, and future security enhancements.
